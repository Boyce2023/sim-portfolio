# case: 后台任务的三重盲区 — 不看 / 看了也被骗 / 骗我的是我自己写的脚本

**类型**: 执行纪律 + 工具使用（非交易判断）
**严重度**: P0 — 用户连续两条消息追问，第二条直接点名我违反了自己的规则

## 用户原话

> 你为什么老超时，自己还不知道自己超时呢，好奇怪，你到底在干嘛，你不随时监控？还是你放在后台了，就不能往前面放了？

> 我记得我们有规则吧，就20分钟没反应就去看一下

规则确实有，全局 §底层执行铁律 第2条：**"20分钟无进展 / 20次报错 = 强制主动复查修复，不反复重试拖时间、绝不等用户问"**。

---

## 三重盲区，一层套一层

| 层 | 我做错的 | 后果 |
|---|---|---|
| **① 不看** | 14:31 起后台任务，14:31→15:00 共29分钟零复查，等用户问"咋样了"才去看 | 直接违反20分钟铁律 |
| **② 看了也被骗** | 抓取脚本的 `except TO`（超时）分支只 sleep 不计数，三次重试用完直接跳出，`fail` 计数器压根没加 | **55天抓取失败，心跳一直显示 fail=0**。就算我中途去看，也会看到"一切正常" |
| **③ 上一个任务同样形状** | 行业映射脚本 131个行业失败113个，**照常打印 DONE、照常写文件**，产出一个14%覆盖率的 map | 直到用户问才发现 |

②和③是同一个病：**失败没有被计数/没有被显式建模，于是"跑完了"和"跑挂了"在输出上长得一样。**

---

## 为什么"超时"这件事本身也是我的错

第一次拉行业映射我用了前台 Bash，默认 timeout 是 120s，而我**明知道**131个行业要三四分钟。我可以传 `timeout` 最长到 600000ms，也可以一开始就 `run_in_background`。两个都没做，然后被超时打断。

**"老超时"不是工具限制，是我没设参数。**
**"放后台就拿不到进度"更不是——心跳文件一秒就能 cat 出来。真实原因是我没去 cat。**

---

## 机械动作（不靠自觉）

1. **任何后台任务，起完立刻挂 Monitor**，而且 Monitor 的 filter 必须同时覆盖成功路径和失败路径（进程死了/卡住也要告警）。只 grep 成功标志的监控，在崩溃时的表现和"还在跑"完全一样。
2. **任何 retry 循环，每一条 except 分支都必须计入 fail**。写完先自问：如果这里连续失败20次，我的计数器会不会还是0？
3. **任何"DONE"必须带覆盖率断言**。`fetch_ind2.py` 已加：`if len(m)<3000: sys.exit(1)`，宁可报错退出也不产出一个86%空的文件。
4. **前台 Bash 跑超过90秒的东西 = 一开始就该 run_in_background**，不要等它被120s默认值掐。
5. 起任务时就算好预计时长，**到点没完就是异常**，不是"再等等"。
